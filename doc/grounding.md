# 사실·근거 검증 사용 가이드

v2 장애 대응은 수집한 관측 자료와 문서 원문을 기준으로 답변을 구성하고 검증합니다.
검증 규칙과 렌더링은 `agent/grounding.py`에 있으며 모델 제공자에 의존하지 않습니다.

## 작성과 검증 순서

1. 서비스별 모니터링과 런북 원문을 출처 ID·참조·수집 시각과 함께 기록합니다.
2. 서비스 상태·CPU·메모리·알림 원문은 코드에서 `Fact`로 구성합니다.
3. 모델은 `DraftAnnotations`로 가설·추가 확인 사항·런북 문서/단계 선택만 반환합니다.
4. 선택한 단계의 인용문은 코드가 문서 원문에서 가져와 `DraftReport`에 결합합니다.
5. 사실의 출처·서비스·필드·값·단위와 인용문·단계·서비스 연결을 대조합니다.
6. 통과한 초안만 최종 답변으로 렌더링합니다. 반려되면 오류 사유를 전달하여 재작성합니다.

모델 주석의 예시는 다음과 같습니다. `facts`나 `quote`를 모델이 반환하면 형식 오류로 반려합니다.

```json
{
  "hypotheses": ["부하 증가 가능성"],
  "missing_checks": ["프로세스 상세 확인 필요"],
  "recommendations": [{"source_id": "source-book", "step": 1, "target": null}]
}
```

`recommendations`는 실행한 조치가 아니라 참고할 문서 단계의 선택입니다.
실제 수집한 문서 ID와 존재하는 단계를 지정해야 합니다.
문서와 서비스의 연결이 확인되지 않았으면 `target`을 비우고 **공통 참고 · 서비스 적합성 미확인**으로 표시합니다.
현재 런북 수집은 기존 공통 규칙을 사용합니다. 서비스별 검색과 적합성 개선은 별도 기능입니다.

## 검증 범위

- 모니터링 성공 자료만 사실의 근거로 사용합니다. 미확인·오류·모델 분석·런북은 관측 근거가 아닙니다.
- 출처 ID, 요청한 서비스, 필드, 수치, 단위가 일치해야 합니다. 문자열 숫자를 수치로 묵시적으로 변환하지 않습니다.
- 수집한 사실의 누락·중복, 현재 조사에서 선택한 정상 근거 대신 과거 근거 사용도 검사합니다.
- 런북 단계와 인용 원문을 대조합니다. 특정 서비스의 참고 절차로 표시하려면 `applicable_targets`에 해당 서비스가 있어야 합니다.
- 가설·추가 확인 사항에 수치를 반복하거나 미조사 서비스, 미수집 로그 분석·조치 완료를 단정하는 표현을 검사합니다.
- Ollama 생성 설정에는 정성 서술의 숫자를 줄이고 각 배열을 한 항목으로 작성하도록 형식 힌트를 줍니다.
  생성 형식만으로 내용을 신뢰하지 않고 공통 검증기를 적용합니다. 숫자를 포함한 ID를 서술에
  반복하는 대신 해당 서비스·인스턴스처럼 표현할 수 있습니다.

알림에 포함된 숫자는 **알림 원문**으로만 표시합니다. 예를 들어 알림의 고정 임계값이나
과거 수치를 현재 CPU 측정값으로 바꾸지 않습니다. 모델 분석은 관측 자료와 분리합니다.

**통과 범위는 구조화된 관측 사실과 문서 원문 인용의 일치입니다.** 자유 서술의 의미를
모두 자동으로 증명하거나 장애 원인을 확정하지 않습니다. 가설은 미검증 추정으로 구분하며,
서비스별 문서 적합성이나 조건부 조치의 실행 가능성도 이 검증만으로 보장하지 않습니다.

## 실패와 제한 응답

최초 작성 1회와 재작성 2회를 합쳐 최대 3회 작성합니다.
3회 모두 실패하면 강제로 통과시키지 않습니다.

| 상태 | 의미 |
|---|---|
| `validation_status=passed` | 사실·인용 대조 통과. 가설의 진위를 확정한 것은 아님 |
| `validation_status=failed`, `processing_status=validation_failed` | 최대 시도 후 검증 실패. 확인 가능한 관측 사실만 표시 |
| `validation_status=not_run` | 확인 질문·일반 대화·정상 관측 자료 없음 등으로 검증 미실행 |

관측 자료가 없으면 작성 모델을 호출하지 않고 자료 부족을 알립니다.
일부 서비스만 수집한 경우에는 수집한 사실의 검증을 통과해도 처리 상태가 `partial`일 수 있습니다.

검증 중에는 조사·작성·반려·재작성 진행 상황만 표시합니다. 장애 답변의 `AnswerToken`과
초안·모델 입력 프롬프트는 화면으로 보내지 않고 최종 답변만 전달합니다.
일반 대화의 스트리밍은 유지합니다. 대화 DB에도 최종 답변만 저장합니다.

## API에서 확인할 항목

POST `/chat`의 `metadata`와 SSE `/chat/stream`의 `FinalAnswer.metadata`에서 확인합니다.

- `processing_status`: 요청 처리 상태
- `validation_status`: 미실행·통과·실패
- `validation_attempts`: 수행한 검증 횟수
- `validation_scope`: `structured_facts_and_exact_runbook_quotes`
- `validation_history`: 시도별 상태와 실패 사유
- `response_state.validation.issues`: 마지막 검증 오류

대표 오류는 `value_mismatch`, `unit_mismatch`, `target_mismatch`, `source_missing`,
`source_not_observation`, `runbook_quote`, `runbook_target`, `text_numeric_claim`,
`unsupported_observation`, `draft_schema`입니다.
출처 ID와 수집 시각은 요청마다 달라집니다. 독립된 두 실행의 텍스트를 그대로 비교하지 말고
동일 근거 조건에서 사실·처리 상태·검증 상태를 확인합니다.

## 실행과 기능 테스트

실제 Ollama와 서비스 기동은 [대상 확인 실행 가이드](target_scope.md)를 따릅니다.
서비스 폴더에서 전체 기능 테스트를 실행합니다.

```bash
.venv/bin/python -m unittest discover -s tests -v
```

자동 테스트는 잘못된 초안과 근거를 주입하여 반려·재작성 제한·안전한 제한 응답·초안 비노출을 확인합니다.
임시 DB만 사용하며 실제 모델 호출과 `.env` 읽기는 하지 않습니다.
OpenAI 어댑터의 JSON 인터페이스 테스트도 호출 함수를 대체하여 검증합니다.
