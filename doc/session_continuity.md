# 후속 대화와 세션 유지 실행 가이드

v2는 SQLite에 메시지·최종 처리 상태·구조화 문맥을 함께 저장한다. 같은 탭의 새로고침과 동일 DB를 사용하는 서버 재시작 후 대화를 복원한다. 현재 상태를 다시 묻는 요청은 새 모니터링과 런북 검색·검증을 실행한다.

## 실행

[OpenAI 런북 검색 가이드](runbook_search.md)에 따라 키와 인덱스를 준비한 뒤 서비스 폴더에서 실행한다.

```bash
bash sh/run_agent_openai.sh
```

다른 터미널:

```bash
.venv/bin/python web_demo_server.py
```

`http://localhost:8600`에서 사용한다. 기본 DB는 서비스 폴더의 `session.db`이며 `SESSION_DB_PATH` 환경변수로 별도 DB를 지정할 수 있다. 서버 재시작 때 같은 경로를 사용해야 한다. 기존 `messages` 테이블은 유지하고 `conversation_context`, `message_metadata`를 추가한다. 이전 메시지에는 검증 통과를 임의로 부여하지 않는다.

## 후속 질문 예

| 순서 | 입력 | 기대 동작 |
|---|---|---|
| 1 | 메모리가 계속 증가해요 | 어느 서비스인지 확인 |
| 2 | cache-service | 확인 대기 중인 요청에 연결해 조사 |
| 3 | 지금은 정상화됐어? | cache-service의 현재 관측 재수집 |
| 4 | payments-service와 cache-service 상태 확인 | 두 서비스 조사 |
| 5 | 그 서비스 다시 확인해줘 | 두 서비스 중 대상을 확인하고 조사 보류 |
| 6 | cache-service | 선택한 서비스만 새로 조사 |

이번 메시지에 명시한 서비스가 이전 대상보다 우선한다. 알려지지 않은 서비스나 제외한 대상을 이전 서비스로 대체하지 않는다. 일반 인사·잡담은 조사 대상을 자동 적용하거나 확인 대기 요청을 덮어쓰지 않는다. 확인 답변에는 등록된 정확한 서비스 ID를 사용한다. 자유로운 별칭·모든 한국어 지칭을 해석하는 기능은 아니다. 모호하면 확인한다.

현재 상태를 묻는 후속 질문에서 과거 CPU·메모리·알림이나 모델 추정을 재사용하지 않는다. 문맥에는 사용자가 말한 요청·증상, 확인된 대상, 확인 대기 질문, 갱신 시각만 저장한다. 과거 대상도 요청 시 등록 목록에서 다시 확인한다.

## 화면 복원과 새 대화

- 같은 탭에서 새로고침하면 `sessionStorage`의 대화 ID로 메시지를 다시 불러온다.
- 복원한 답변에는 `저장된 답변`과 당시 처리 상태를 표시한다. 과거 결과이므로 현재 상태를 의미하지 않는다.
- 복원 조회는 모델·모니터링·임베딩·재순위화를 호출하지 않는다.
- `새 대화`는 새 ID로 시작한다. 이전 메시지는 DB에 보존하며 이전 조사 문맥은 적용하지 않는다.
- 탭을 닫거나 브라우저 저장소를 지우면 자동 연결을 보장하지 않는다. 이전 대화 목록·계정 간 동기화는 제공하지 않는다.
- 복원 실패 시 전송을 막고 `대화 다시 불러오기`로 재조회한다. 연결이 끊긴 요청은 자동 재전송하지 않는다. 먼저 저장된 결과를 확인한다.
- 복제한 탭이 같은 ID를 이어받을 수 있다. 별도 대화가 필요하면 `새 대화`를 사용한다.

프런트엔드 기본 실행은 로컬 주소에만 바인딩한다. 이 데모는 인증·권한을 갖춘 다중 사용자 서비스가 아니며, 대화 ID는 접근 권한 체계를 대신하지 않는다.

## API

`POST /chat`과 `GET /chat/stream`에 같은 `thread_id`를 전달하면 같은 문맥을 사용한다. 다른 ID는 별도 대화다. 대화 ID는 영문·숫자·하이픈·밑줄, 길이 1~128자를 허용한다.

`GET /sessions/{thread_id}`는 메시지·저장된 메타데이터·문맥을 반환한다. 존재하지 않는 ID는 빈 이력으로 반환하며 조회 결과를 캐시하지 않는다. 모델을 호출하지 않는다.

응답 `metadata.context_resolution.mode`:

| 값 | 의미 |
|---|---|
| explicit | 이번 메시지에서 대상 결정 |
| previous_target | 이전에 확인한 대상 연결 |
| clarification_answer | 확인 답변을 원래 요청에 연결 |
| ambiguous_reference | 여러 대상 등 추가 확인 필요 |
| pending_clarification | 해결되지 않은 확인 질문 유지 |
| missing_target | 사용할 대상 없음 |
| registry_error | 등록 목록 오류 |

같은 프로세스의 동일 대화 요청은 문맥 로드부터 최종 저장까지 순서대로 처리한다. 메시지 쌍·메타데이터·문맥 중 저장 실패가 발생하면 전체를 롤백한다. 잘못 저장된 문맥은 임의로 복구해 조사하지 않고 오류를 반환한다. SSE 저장 오류는 `Error` 이벤트로 알리고 `FinalAnswer`를 보내지 않는다.

현재 기본 실행은 단일 서버 프로세스와 로컬 SQLite 기준이다. 이력 조회는 해당 대화 전체를 반환한다. 여러 서버 프로세스 간 동시 처리·장기 이력 페이지 나누기·과거 대화 선택 UI는 별도 확장 범위다.

## 검증

```bash
.venv/bin/python -m unittest discover -s tests -v
```

실제 OpenAI 확인에는 별도 테스트 DB와 샘플 대화만 사용한다. 실제 메시지 전송은 API 비용이 발생한다.

OpenAI API 요청에 필요한 문맥을 애플리케이션이 전달한다. 원격 Conversation 저장 API를 새로 사용하지 않는다. [공식 대화 상태 설명](https://developers.openai.com/api/docs/guides/conversation-state#manually-manage-conversation-state)
